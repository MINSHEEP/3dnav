# M701（RS485）接入说明

## 1. 接线与供电

M701 使用 RS-485 两线半双工，不使用 RS-422 四线模式。

| M701 | CH348 | 说明 |
| --- | --- | --- |
| A | T/R+ | RS-485 正线 |
| B | T/R- | RS-485 负线 |
| GND | GND | 必须共信号地 |
| VDD | 独立 5.0±0.2V 电源 | 电源需能持续提供 500mA |

CH348 的 `RXD+`、`RXD-` 和 `VCC` 不接 M701。M701 的 CO2 传感器有约 300mA 瞬态需求，不要默认用转换器 VCC 给模块供电。若完全无响应，可在断电后对调 A/B 再试；修改 M701 地址拨码后必须重新上电。

## 2. 串口与协议

- 9600 bps、8数据位、1停止位、无校验、无流控。
- 默认示例地址为1；3位拨码支持0到7，厂家建议不要使用0。
- 主站每秒读取一次，不能快于500ms。
- ROS话题：`/air_quality/m701`（`std_msgs/msg/String` JSON）。
- 页面只显示通过地址、功能码、长度和CRC16校验的完整数据；失联或坏帧会清空旧值。

## 3. 按实际芯片确认驱动（仅必要时安装）

不要根据包装上的 CH341/CH348 名称直接覆盖驱动。新版连接设置读取 Linux 实际生成的 USB 串口及驱动信息，兼容标准 `ttyUSB*` 和厂商 `ttyCH341USB*`、`ttyCH348USB*` 命名；前提是当前系统驱动已经支持实际芯片并生成串口。已有正常串口时无需重装驱动，页面也不会安装、卸载或切换内核驱动。

附件 `摩可灵-CH348-driver-linux.zip` 内是 WCH CH340/CH341 内核驱动 V1.8（2024-08），支持的 USB VID:PID 包括 `1a86:7523`。该驱动加载后创建 `/dev/ttyCH341USB0`、`/dev/ttyCH341USB1` 等设备，而不是内核自带驱动常见的 `/dev/ttyUSB0`。

先检查 Ubuntu 内核自带驱动是否已经可用：

```bash
lsusb -d 1a86:
sudo modprobe ch341
dmesg | tail -n 30
ls -l /dev/ttyUSB* 2>/dev/null
```

如果已经出现可正常读写的 `/dev/ttyUSB0`，M701 的9600 8N1通信不依赖厂商扩展功能，可以继续使用内核自带驱动。若必须安装附件中的厂商驱动，先停止占用串口的ROS进程，然后执行：

```bash
sudo apt update
sudo apt install build-essential linux-headers-$(uname -r) unzip

mkdir -p ~/ch348-driver
unzip '摩可灵-CH348-driver-linux.zip' -d ~/ch348-driver
cd ~/ch348-driver/摩可灵-CH348-驱动

make clean
make
modinfo ./ch341.ko | grep -E 'version|description|license'

# 先临时加载并验证，不要一开始就覆盖系统模块。
sudo rmmod ch341 2>/dev/null || true
sudo insmod ./ch341.ko
dmesg | tail -n 30
ls -l /dev/ttyCH341USB*
```

确认临时加载和串口通信正常后，才执行永久安装：

```bash
sudo make install
sudo depmod -a
```

厂商 Makefile 会把 `ch341.ko` 写入当前 `/lib/modules/$(uname -r)/kernel/drivers/usb/serial/`，不是 DKMS：升级内核后需重新编译安装。安装脚本还会用 `|| true` 忽略部分失败，所以必须以上面的 `dmesg`、`modinfo` 和设备节点检查为准。

安装前运行 `mokutil --sb-state`。若 Secure Boot 已启用，附件中的未签名模块可能报 `Key was rejected by service`；此时应使用内核自带驱动，或按单位的内核模块签名流程签名并登记密钥，不要把“关闭安全启动”当成默认处理。

## 4. 控制板部署

先确认转换器的稳定设备名和串口权限：

```bash
ls -l /dev/ttyCH341USB* /dev/serial/by-id/ 2>/dev/null
sudo usermod -aG dialout "$USER"
sudo apt install python3-serial
```

加入 `dialout` 后需注销并重新登录。若厂商驱动仍生成 `/dev/serial/by-id/...`，优先使用该稳定路径；否则单个CH348通常为 `/dev/ttyCH341USB0`。项目中还保留了旧串口底盘代码，选择端口时必须确认没有被其他进程占用。

当前部署主机使用内核 `ch341` 驱动，已通过真机通信确认以下稳定路径对应
M701 的 CH340 USB-RS485 转换器：

```text
/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0 -> ../../ttyUSB0
```

重新编译并启动常驻后台：

```bash
cd /home/a/3dnav
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select lzp_interface car_vel
source /home/a/3dnav/install/setup.bash

ros2 launch car_vel launch_manager.launch.py
```

M701 默认随主启动文件运行，默认使用
`/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0`、地址1。仅在更换串口、
USB-RS485 转换器或拨码地址后，可在设置页重新绑定；尚未保存页面配置时也可通过 `m701_port`、`m701_address`
参数覆盖默认值。其他主机如果没有这个 `by-id` 路径，应先确定实际稳定设备名，
不要直接回退到可能被底盘串口占用的 `/dev/ttyUSB0`。

验证：

```bash
ros2 topic echo /air_quality/m701
```

看到 `online:true`、`valid:true` 和七项 `values` 后，打开 `inspection.html` 或 `remote_control.html` 即可看到同一组实时数据。首次上电前5分钟页面显示“传感器预热中”；说明书要求避免把该模块用于人身安全系统，因此本接入只做监测展示，不驱动急停或安全告警。

## 5. 设置页绑定与换转换器

更新后先让机器人安全停止，再停止旧后台、编译上述两个包、重新加载工作区并按原方式启动后台。刷新浏览器设置页：

1. 在“气体传感器连接”中刷新设备；核对 USB 标识、实际驱动和设备位置。列表枚举不会向串口发送命令。
2. 选择接在 M701 上的转换器，推荐“自动重连已绑定设备”；默认 9600、地址 1，地址必须与模块拨码一致。
3. 勾选确认，点击“测试连接”。仅查询已确认设备一次，校验地址、功能码、长度和 CRC；不会修改传感器寄存器。测试会暂时中断采样，结束后恢复原连接配置，测试结果不会用于告警。
4. 测试通过后点击“保存并重新连接”。配置保存在后台运行用户的 `~/.ros/robot_navigation/m701_connection.json`，优先于启动参数，星玑和钢镚共用，不随本体切换。

自动模式按 USB 标识、序列号、接口和通道找回设备，不依赖 `ttyUSB0` 等编号。没有序列号时绑定物理 USB 位置；重复序列号会结合明确选择的位置绑定。更换转换器、移动无序列号设备的插口或驱动改变身份信息后，需要重新确认保存。无法唯一确定时停止连接，不尝试其他串口。物理位置绑定无法区分同一插口上完全相同且无唯一序列号的替换设备，仍须由操作人确认。

固定路径模式也检查绑定身份，不会因编号被其他设备复用而自动接入。配置损坏时停止采样，在设置页重新确认并保存即可修复。保存失败保留原配置；多页面旧版本保存会被拒绝，需要刷新。

页面区分设备缺失、权限不足、串口占用、传感器无响应和回包校验失败；识别到 WCH USB 但未发现串口时提示核对芯片与驱动，而不是自动安装驱动。串口使用独占锁，但仍应关闭其他串口调试程序，不要同时运行多个采集后台。

断线重连、测试或配置更新后重新计时预热，旧读数不会作为有效新数据使用。现有巡检语音提示继续遵守预热和有效性条件，不能代替专业安全报警设备。

验收时依次检查：正常查询、拔掉后离线、同设备插回自动恢复、编号改变后仍找回原设备、其他串口不被误连，以及切换两种本体后气体连接配置不变。新连接状态话题为 `/air_quality/m701/connection`，配置服务为 `/air_quality/m701/configure`。

## 6. 旧串口路径不存在时的恢复（2026-10-15）

出现“指定串口不存在或不唯一”表示尚未取得串口，不是 CO₂ 数值超标，也不能直接认定驱动缺失。默认旧路径可能在更换转换器、驱动或小电脑后不再存在。本次改动只涉及 M701 连接诊断、设置页和回归测试，不更改星玑、钢镚或导航参数。

先将修改后的源码同步到小电脑。确认机器狗安全停止，结束任务并在原终端正常停止后台，然后重新编译：

```bash
cd /home/a/3dnav
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select car_vel
source /home/a/3dnav/install/setup.bash
```

在同一个已加载工作区的终端，可先执行只读诊断。该命令只枚举 sysfs、读取串口连接配置，不打开串口、不发送 Modbus、不安装驱动，也不需要 ROS 节点正在运行：

```bash
/usr/bin/python3 -m car_vel.m701_connection
```

诊断输出的 `diagnostic.code` 含义：

| 状态 | 含义与处理 |
| --- | --- |
| `serial_not_found` | 没有发现任何 USB 串口。先单独执行 `lsusb` 核对适配器是否被枚举；若没有，检查 USB 连接和供电，不能靠更改页面路径解决。 |
| `driver_missing` | 发现 WCH USB 设备，但没有对应串口节点。核对输出中的实际 VID:PID、芯片及内核日志；该状态不等于已证实缺少哪个驱动，不要盲目覆盖内核模块。 |
| `usb_claimed` | WCH USB 接口由 `usbfs` 接管且没有串口，可能有用户态程序占用。核对输出的当前 `usb_node`、接口驱动和内核日志；不能仅凭 `usbfs` 认定具体占用者，也不会自动停用辅助服务。 |
| `selection_required` | 旧路径不存在，且只有一个已知候选串口。页面推荐该设备，但必须核对接线、勾选确认、测试并保存后才按新配置连接。 |
| `ambiguous_selection` | 有多个候选串口，程序不会猜测或轮流探测；按实际接线在设置页选择。 |
| `path_changed` | 固定路径失效，但找到了同一绑定身份。页面推荐改为自动重连，仍需人工确认并保存。 |
| `device_missing` / `identity_changed` / `ambiguous` | 原身份不存在、编号被复用或身份不唯一；不自动切到另一个适配器。更换硬件后需要重新绑定。 |
| `configured` | 已找到配置指定的串口，仅说明路径/身份匹配；还必须收到有效 M701 数据才算在线。 |
| `config_error` | 连接配置不能安全读取；在设置页重新核对并保存，不会悄悄改用默认设备。 |

重新启动后台：

```bash
ros2 launch car_vel launch_manager.launch.py
```

浏览器按 `Ctrl+F5` 刷新设置页。在“气体传感器连接”中刷新设备，选中并确认实际连接 M701 的转换器，选择“自动重连已绑定设备”，设置与拨码一致的地址（原配置为 1）和 9600 波特率。依次执行“测试连接（不保存）”和“保存并重新连接”。只有测试取得 CRC 等校验通过的数据，才说明传感器链路可用；推荐设备、配置保存成功或普通串口打开成功都不能代替此验证。

另开终端验证采样：

```bash
source /opt/ros/humble/setup.bash
source /home/a/3dnav/install/setup.bash
ros2 topic echo /air_quality/m701 --once
```

应有 `online:true`、`valid:true` 和 `values`。预热期间可显示数据，但现有告警仍须等待预热结束。同一故障日志最多每 30 秒重复一次；故障变化或恢复后再次故障会立即记录，离线数据状态仍按采样周期持续发布，不保留旧值冒充新值。

## 7. 已确认的 CH340 / BRLTTY 冲突

现场 2026-10-15 的内核日志记录：

```text
ch341-uart converter now attached to ttyUSB0
usbfs: interface 0 claimed by ch341 while 'brltty' sets config #1
ch341-uart converter now disconnected from ttyUSB0
```

这是 `ch341` 已正常工作、随后被 BRLTTY 抢占的证据，不是必须换 CH348 驱动或重新编译 SDK。BRLTTY 为盲文辅助功能服务；**若这台电脑需要盲文设备，不得直接停用，应按厂商/系统维护方案对该串口转换器做针对性规则调整**。

先只读核对实际安装的服务：

```bash
systemctl list-unit-files 'brltty*' --no-pager
```

只有在操作者确认不使用 BRLTTY 辅助功能、机器狗安全静止、且上述列表确实包含 `brltty.service` 和 `brltty-udev.service` 时，才临时停用这两个服务，防止拔插后再次抢占：

```bash
sudo systemctl mask --runtime --now brltty.service brltty-udev.service
```

随后仅拔插**气体传感器的 USB-RS485 转换器**，不要拔插雷达网卡、相机或其他设备。检查：

```bash
sudo udevadm settle --timeout=10
lsusb -t
ls -l /dev/ttyUSB* /dev/ttyCH34* /dev/serial/by-id/
```

预期看到 `Driver=ch341`（或现场已经验证的厂商串口驱动）以及实际串口节点，内核不再紧跟 BRLTTY 抢占/断开日志。然后按第5节测试并绑定 M701，检查有效 CRC 数据。旧稳定路径若重新出现，原后台的自动重试即可恢复，修复 BRLTTY 冲突本身不要求重编译项目。

`--runtime` 的屏蔽只持续到重启，不卸载软件、不永久改变开机配置。撤销临时屏蔽：

```bash
sudo systemctl unmask --runtime brltty.service brltty-udev.service
```

撤销后若需使用辅助功能，应按原配置启动相关服务；它们也可能由下一次设备事件启动。屏蔽仍在时不要手动启动 BRLTTY。是否长期屏蔽或仅修改匹配该转换器的规则，应在验证 M701 恢复且明确辅助功能需求后单独决定，不由程序自动处理。

USB 的设备编号会在拔插后变化，不能持续复用旧的 `/dev/bus/usb/001/004`。可通过第6节只读诊断获取当前 `usb_node`，再检查其占用情况。

BRLTTY 官方说明确认 USB 设备规则可自动启动服务：[Using Systemd Service Management](https://brltty.app/doc/Systemd.html)。本项目只读取状态、提示冲突；不会自动屏蔽、卸载或重启 BRLTTY。

## 8. 已确认不使用盲文设备时的长期防抢占

本节适用于已确认不使用 BRLTTY 盲文辅助功能、且操作者明确选择长期防抢占的机器人小电脑。
现场已核对单元名称为 `brltty.service` 和 `brltty-udev.service`，并验证临时屏蔽后 M701
能收到有效数据。需要使用盲文设备的电脑不要采用本节，应改用针对转换器的规则维护方案。

本措施只解决已证实的 BRLTTY 抢占，不安装或替换 CH341/CH348 驱动，不改 M701
已正常的接线、波特率和地址，不修改星玑、钢镚、雷达或导航配置，也不卸载软件。
这些是目标 Ubuntu 的一次性系统配置操作，不是 ROS 源码编译步骤；仅同步本文档不会让配置自动生效。

### 8.1 一次性持久屏蔽

让机器狗保持静止，在小电脑终端执行：

```bash
sudo systemctl mask --now brltty.service brltty-udev.service
```

这里刻意不带 `--runtime`，持久屏蔽写入 `/etc/systemd/system/`，重启后仍生效。
现有 `/run` 下的临时屏蔽可以保留，不必先解除，以免出现重新激活的空窗。
`--now` 同时停止这两个服务。若出现 `File exists`、权限错误或单位名称与现场不符，
保留输出供核对，不加 `--force` 覆盖已有本地单元。

检查持久链接和服务状态：

```bash
ls -l /etc/systemd/system/brltty.service /etc/systemd/system/brltty-udev.service
systemctl is-enabled brltty.service brltty-udev.service
systemctl is-active brltty.service brltty-udev.service
```

预期两个 `/etc/systemd/system/` 链接都指向 `/dev/null`，启用状态都是 `masked`，
运行状态都是 `inactive`。被屏蔽或未运行时，检查命令返回非零退出码是正常的；
不要把多条检查串成只有上一条成功才执行的 `&&` 链。仅出现 `/run` 下链接、
`masked-runtime`、`disabled` 或 `static` 都不能代替这项持久核验。

当前串口和采样正常时，不需要拔插、重探测、重启后台或立即重启电脑。
正常运行的后台可按下面命令核验有效数据：

```bash
source /opt/ros/humble/setup.bash
source /home/a/3dnav/install/setup.bash
timeout 10s ros2 topic echo /air_quality/m701 --once --full-length
```

应有 `online:true`、`valid:true`、非空 `values` 和空 `error`。预热状态遵守现有规则，
不因为屏蔽服务而跳过。等下一次正常、安全重启小电脑并按原方式启动机器人后台后，
重新检查 `masked`、实际串口存在及有效数据，才能完成跨重启验收；不为测试擅自重启机器人。

### 8.2 撤销长期配置

只有以后确实需要恢复 BRLTTY 时再执行；这可能重新引入本转换器的抢占冲突：

```bash
sudo systemctl unmask brltty.service brltty-udev.service
sudo systemctl unmask --runtime brltty.service brltty-udev.service
```

两条分别撤销持久和可能残留的临时屏蔽。不自动执行 `enable` 或 `start`，因为现场原状态
是 `brltty.service` 为 `disabled`、`brltty-udev.service` 为 `static`；后续按辅助设备要求维护。

持久屏蔽与临时屏蔽语义依据：[systemd v249 官方 systemctl 文档](https://raw.githubusercontent.com/systemd/systemd/v249/man/systemctl.xml)。
